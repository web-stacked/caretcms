# CaretCMS 0.6.3

This release makes CaretCMS safe to run next to developers who keep working on
the site. An editor's unpublished draft no longer hides changes a developer
commits afterwards, and a developer's change to a template no longer seems to
do nothing because of a value an editor saved earlier.

Most of these problems came from a field report by someone who ran 0.6.1 on a
live static site and took it off again the same day. Every one of their
incidents was reproduced, and each fix was tested on a real site in dev, on a
static build and on a production Node server.

`@caretcms/caretize` 0.6.1 gains two commands: `caretize doctor`, which checks a
site that already uses CaretCMS, and `caretize remove`, which takes CaretCMS out
again without losing your work. `--restore` no longer overwrites files you edited
after caretize ran.

## Upgrading

Install `@caretcms/core@0.6.3` and `@caretcms/caretize@0.6.1`. Then run:

```bash
npx @caretcms/caretize doctor
```

It lists drafts nobody has published, content Git hasn't committed and anything
in `.gitignore` that would break a deploy. It changes nothing.

### Content files

The first time an editor saves text that is written in a template (rather than
read from a collection), its content file gains a short `__caret_template__`
block. It records which template text the saved value replaced. Commit it with
your content. It never reaches your pages or the Studio.

```yaml
headline: "Our best work"
__caret_template__:
  headline: t38925866
```

Astro's content collections ignore unknown keys. If a collection's Zod schema
uses `.strict()`, declare the key or the build fails; `caretize doctor` tells you
when this applies:

```ts
__caret_template__: z.record(z.string(), z.string()).optional(),
```

Values saved before this release have no record, so they keep replacing the
template's text until their entry is next saved or published.

### Git on publish

With `CARET_GIT_ON_PUBLISH=true`, Publish now commits the images the published
entries use. Don't list your uploads folder (usually `public/uploads/`) in
`.gitignore`.

### API and adapters

A publish conflict for a field changed on both sides now lists those fields in
`conflicts[].fields`. A new conflict reason, `uncommitted_source`, holds back an
entry whose file has uncommitted changes; send `{ "allowUncommitted": true }` to
`POST /api/cms/publish` to include them.

`GET /api/cms/draft` lists drafts that need a decision in `conflicts`, and
`POST /api/cms/draft` with `{ "collection", "id", "keep": "mine" | "site" }`
settles one. The bundled editor does both.

`UploadHandler` has a new optional method, `localFile(url)`, for handlers that
write uploads into the project. Custom handlers don't need it.

## Drafts and newer content

A draft used to be a full copy of the entry, taken when the editor first saved.
If a developer then committed a new image or a new section to the same file,
the signed-in editor kept seeing the old copy, so the change seemed to revert.
Publish refused the entry, and its message sent the editor back to the same
stale page.

Now a draft only changes the fields the editor edited. Everything else follows
the published entry, on the page, in the Studio and when publishing. When the
editor and someone else changed the same field, the toolbar shows
**1 needs your choice** and a dialog with both versions: **Keep mine** or
**Use the site's version**. The editor's other changes aren't affected. A draft
of an entry that was deleted on the site asks whether to keep or drop it.

## Body text follows its paragraph

Edits to Markdown body text were tied to a paragraph's position in the file.
When someone added a paragraph above, the edit vanished from the page, could
show up inside a different paragraph, and blocked Publish until it was
discarded.

An edit now stays with the paragraph it was made on and publishes there. If the
paragraph itself was rewritten, the editor sees their text with
**Copy my text** and **Drop my edit**.

## Template text

Text typed into a template and a value an editor saved for it are two sources
for the same words. The saved value always won, so a developer who changed a
heading in the template saw no change in dev or in the build.

The saved value still shows while the template says what it said when the value
was saved. Once the template's text changes, the newer template text shows, the
dev server and the build log name the binding, and the next save or publish of
that entry removes the old value. An editor who edits that text again replaces
the template as before. See
[saving and visibility](../saving-and-visibility.md#text-written-in-templates).

The dev server also picks up a template edit straight away. It could keep
showing a binding's old template text until a page using that template had
been opened.

## Git and uploads

With `CARET_GIT_ON_PUBLISH=true`:

- Publish asks before it commits a content file that has someone else's
  uncommitted changes. Before, a developer's unfinished edit was committed with
  the editor's change, under the editor's name. **Publish anyway** includes
  them; other entries in the same publish go through either way.
- The images the published entries use are committed just before their content.
  Before, only the content file was committed, so a site deployed from Git
  showed a broken image after an editor replaced one.

Discarding a draft now deletes the images uploaded only for it. They used to
stay in `public/uploads/` and ship in the next build.

## caretize

`caretize doctor` checks a project that uses CaretCMS: the installed version,
the config, unpublished drafts per editor and how old they are, content and
uploads Git hasn't committed, uploaded images nothing uses, `.gitignore`
mistakes and a `.strict()` schema that would reject `__caret_template__`. Each
finding says what to do. It exits 1 when something would break a deploy.

`caretize remove` takes the `data-caret` attributes out of your templates as
they are now, removes `caret()` from `astro.config` and offers to uninstall the
package. Everything else in the files stays, including work done since caretize
ran. It then lists what's left: text saved in the browser over template text
(the site will show the template's own text again, so copy what you want to
keep), `.caret/`, and the `.env` and `.gitignore` lines.

`caretize --restore` put the backed-up file back over whatever was there, so a
template edited after caretize ran lost those edits with no warning. It now
restores only files that are still exactly what caretize wrote, names the ones
it left alone and points to `caretize remove`. `--restore --force` restores them
anyway. After `caretize init`, it also puts back `astro.config` and
`.gitignore`.

## Also fixed

Publish no longer writes an entry whose edits were undone. A draft that matches
what visitors already see is cleared instead of being saved with a new revision
and a History entry.

## Requirements

Node.js 22.12 or newer, and Astro 6 or 7. Tested on Astro 6.0.0 and 7.2.4 with
Node 22.12 and 24, on Cloudflare (KV, R2 and Durable Objects), and by hand on a
static site and a production Node server. `@caretcms/cloudflare` and
`@caretcms/zod` stay at 0.6.0 and work with core 0.6.3.

The [changelog](https://github.com/web-stacked/caretcms/blob/v0.6.3/CHANGELOG.md)
lists every change.
